## 1. Summary

Proposal to add sidecar tunnel support to the `@capgo/capacitor-video-player` plugin (v8.2.16). A sidecar tunnel would enable the plugin to proxy media requests through a sidecar process/tunnel, potentially for DRM license forwarding, signed URL resolution, or geo-bypass of media endpoints.

---

## 2. Critical Finding — Domain Mismatch

**Repository analysis confirms:** This repository (`capacitor-video-player`) is a Capacitor **video player plugin**, not a tunneling or proxy infrastructure package. There is no existing "sidecar tunnel" concept anywhere in the codebase.

The only "sidecar" references are in iOS native Swift code referring to **sidecar subtitles** (subtitle files loaded alongside progressive MP4/WebM media):
- `ios/Sources/VideoPlayerPlugin/FullscreenVideoPlayer.swift` — "MP4 + sidecar subtitles"
- `ios/Sources/VideoPlayerPlugin/HLSSubtitleResourceLoader.swift` — resource loader for sidecar subtitles

Adding sidecar tunnel support would be a **brand-new feature outside the video player domain**. The tunnel infrastructure more naturally belongs in the **main application**, not in this plugin.

---

## 3. Proposed Feature Scope

If the Product Owner decides sidecar tunnel support belongs in this plugin, the scope would include:

| Area | Description |
|------|-------------|
| **TypeScript API** | New `tunnel` option in `capVideoPlayerOptions` (URL, auth, protocol) |
| **Web implementation** | `src/web.ts` — proxy media requests through tunnel before feeding to `<video>` |
| **iOS native** | `ios/Sources/` — configure AVPlayer/URLSession to route through sidecar tunnel |
| **Android native** | `android/src/main/` — configure ExoPlayer data source through tunnel |
| **Documentation** | README API docs, platform setup, tunnel configuration |

---

## 4. Alternative: Tunnel in Main Application

If the sidecar tunnel belongs in the main application (recommended based on domain analysis):

- The application implements the tunnel (HTTP proxy, WebSocket tunnel, etc.)
- The application passes resolved media URLs to `VideoPlayer.initPlayer({ url: <tunnel-resolved-url> })`
- The plugin remains focused on video playback, not networking infrastructure

---

## 7. Acceptance Criteria (Draft)

- AC-1: `TunnelOptions` interface defined in `src/definitions.ts`
- AC-2: Web implementation can route media through tunnel before playback
- AC-3: iOS native can configure AVPlayer to use tunnel for media requests
- AC-4: Android native can configure ExoPlayer to use tunnel for media requests
- AC-5: Tunnel failure falls back to direct URL (or reports error gracefully)
- AC-6: README auto-generated docs updated via `bun run docgen`
- AC-7: `bun run verify` passes (iOS, Android, Web)
- AC-8: `bun run check:wiring` passes

## 8. Open Questions for Pre-Sync

1. **Domain decision:** Should sidecar tunnel live in this plugin or the main application?
2. **Tunnel protocol:** HTTP CONNECT proxy, WebSocket tunnel, or custom protocol?
3. **Auth:** How are tunnel credentials passed (headers, tokens, cookies)?
4. **DRM interaction:** Does tunnel proxy DRM license requests (FairPlay/Widevine) as well as media?
5. **Scope:** Is this a v9 (breaking) feature or can it be backward-compatible in v8?
